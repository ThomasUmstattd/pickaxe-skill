# Testing and verification

How to run a test on this platform without damaging a live tool, and how to make sure the thing you tested is the thing that shipped. Deciding whether an output is any good is a separate problem, covered in `grading-and-fixtures.md`.

In this file:

## Never iterate on a live tool

There is no dry-run: `run_pickaxe_completion`'s config parameter does not override the prompt, so testing a variant means writing it somewhere real. Keep at least one private staging Pickaxe and iterate there.

A staging workflow that has held up in production:

1. **Check out**: copy the live tool's full field set onto the private staging bot: role, model reminder, the prompt frame and its raw HTML twin, model, temperature, reasoning effort, knowledge document attachments, the token budgets (the reserved-tokens value and the computed budget object), the document upload mode, and the type flags when the tool is a form-plus-chat hybrid. Overwrite everything, so nothing leaks from the previous checkout. Copy the reserve explicitly: a staging bot can inherit a reserve larger than the model's context window from a previous occupant, a partial update never touches a field you do not name, and a null budget silently breaks every upload path on the bot (see the knowledge-base reference). The prompt frame is the field most often forgotten, and forgetting it stages a bot with the persona and nothing else. In one workspace audit, 72 of 88 tools kept at least half their prompt text in the frame, and every form field lives there. The upload mode (`documentuploadtype`) is the field most often never known about: a freshly created or cloned bot sits at the owner-only value, which disables the end-user upload widget outright, so a staging bot that omits it can never test the path most document-analysis tools depend on (details under "Verifying form changes").
2. **Verify the checkout**: read the staging bot back and compare against the full set of fields that determine behavior, not the subset you chose to copy. A verify that only compares what the copier remembered always agrees with the copier. A real checkout printed a clean verification over an empty prompt frame exactly this way.
3. Iterate on the staging bot with `pickaxe_update` and `run_pickaxe_completion`.
4. **Apply**: promote the full set of fields the staging runs actually exercised, prompt and config together. Iteration usually retunes the model, temperature, or deployment type alongside the prompt, and promoting the prompt alone lands it on a combination that exists nowhere in the test record. In one observed case a prompt developed at low temperature on one model would have shipped onto a different model at more than double the temperature, with nothing in the promotion output indicating a problem. Keep an explicit do-not-travel list (the staging bot's name, display title, privacy setting, and any input limits raised to fit test data), snapshot the live config to a file first so rollback does not depend on a possibly stale export, and read the whole promoted set back rather than the subset you named.
5. **Release**: reset the staging bot to an empty state so the next checkout starts clean.

Give staging bots large input limits (`chatinputlength`, `endusertokens`, `membuffer`) so full-length real inputs fit in a completion message. Remember that own-key actions cannot be copied programmatically (actions reference), so action-dependent tools need a manual key attach before end-to-end staging runs.

A staging bot that sat idle between campaigns needs the step 2 check again, for a different reason: nobody performed a checkout to verify. A sandbox kept for one production bot was found carrying a months-old prompt, a different model, an empty model reminder, and zero attached knowledge documents, while the production bot had over a thousand. The first three are visible the moment you read the config. The fourth is the dangerous one, because its symptom is indistinguishable from the result you are trying to measure: with no documents attached, retrieval fails on every run, the bot correctly reports that it found no source, and every arm of a retrieval-dependent A/B returns that same answer. Before trusting any result from a staging bot you did not just check out, diff its config against production and check the attached document count explicitly, since a copy does not carry attachments. Treat a zero count on a retrieval-dependent test as disqualifying rather than as a low number. When the production bot is public and the sandbox is stale, there is no safe place to run the test at all, which is worth discovering before designing the arms.

## A staging number is a screen, not a measurement

Swapping arms across two staging bots rules out one bot being odd. It does not rule out staging as a whole being unrepresentative of the live tool. A prompt change scored 100 percent compliance on two separate staging bots, replicated across a swap, and then 50 percent on the live tool running byte-identical prompt fields. The promotion was clean: only the changed field was written, and the prompt frame, its raw twin, and the reminder were asserted identical between staging and live beforehand. The staging bots differed from live in their output-length cap, which is the leading suspect and was never tested.

Treat a staging figure as a screen that says whether a change is worth promoting, and take the real measurement on the live tool afterward. Budget runs for that live verification rather than declaring victory at promotion. When a staged figure and a live figure disagree, diff the full config rather than the prompt, because the prompt is the part you already know matches.

## Verifying form changes

A staging bot with the live tool's type flags has its own deployment, and every deployment has its own URL. Opening it gives a real, drivable form: field labels, helper text, character counters, and the file input. So the whole rendered widget can be exercised on staging rather than on production. Two settings gate that, and both default wrong on a freshly created or cloned bot. The type flags decide whether a form renders at all, since a forced chat flag leaves a bare chat box (prompt fields reference). And `documentuploadtype` decides who may upload: at the owner-only value the end-user upload control is disabled and the form answers any file with "File uploads are disabled for this Pickaxe". A staging script that does not copy it leaves every staged bot in that state, which makes the upload path untestable while everything else looks correct, and nothing in the output says the field is missing. When a clone behaves as though a whole input channel does not exist, compare its configuration against the source field by field before debugging the prompt.

Three mechanics matter once the form is in front of you:

- **Drive the embed's own URL, not the page that frames it.** The tool renders inside an iframe, so the host page's accessibility tree contains none of the form's elements and element lookups return nothing, even though the form is plainly visible in a screenshot. Read the iframe's `src` and navigate to it directly, where element references and file uploads work normally. Two checks worth running there: a required field is enforced by keeping the submit button disabled rather than by an error message, and the file input's `accept` attribute lists what the client will take, which beats guessing with uploads.
- **A rendered deployment is propagation evidence, not enforcement evidence.** Rendering a deployment's HTML confirms a configured cap or label reached the form (embed deployments only, direct-link deployments refuse to render). The render is intermittently empty, a payload-free shell with zero field labels, so an empty render is not evidence a write failed. Retry until labels appear. And a static render cannot prove runtime behavior, because counters and validation bind to client state a saved page never initializes. Verify enforcement in a live session or record it as unmeasured.
- **Prove a field injects by reading the run's recorded inputs.** Output that looks right does not prove a new field reached the model, which may be inferring the same value from other input such as an uploaded document. A completed run records its submitted inputs as a `Field: value` line above the response in the tool's history. Reading that line is direct evidence the value was captured, and it shows how an empty optional field is represented. Check it before designing a decoy-value experiment, since it usually makes one unnecessary.

## Verify every mutation by reading state back

The single most valuable habit on this platform. Return values confirm the request was accepted. Only a fresh read confirms what happened. Concrete script discipline that has caught real failures:

- After a write, fetch the changed object and compare field by field, or byte for byte for prompt frames.
- Read back every field you set, individually. One update call set three display fields at once, two persisted and one was discarded, so sampling one field and generalizing to the request gets the wrong answer (api-mechanics reference).
- Check the mutation's own response envelope against what you sent before spending a round trip. A returned old value next to your new one is an immediate answer, and most callers never look.
- For surgical edits to config strings, use exact-match replacements and assert each match lands exactly once before writing.
- Refuse to write when live state does not match what you recorded earlier. Drift means another process or person edited the tool, and clobbering it destroys their change silently.

## Platform signals that mislead diagnosis

**The workspace fallback can serve a model you did not choose, at a reasoning effort you did not choose.** Pickaxe has a workspace-wide Fallback Model toggle (Settings, Agent tab) that retries a failed primary model on a backup, for every bot in the workspace at once, and it can be on without the builder having chosen it, so check the tab rather than assuming. A run that fell back is an invisible confound in any quality investigation, and the likely wrong conclusion is a prompt defect that is not there. Since late August 2026 the per-message insights panel shows a fallback indicator when a response came from a model other than the one requested, with three limits: it covers only responses generated after the tracking shipped, it is per-message and UI-only with no per-agent rate and no API access, and workspaces on the strictest privacy setting retain no messages, so they have no diagnostic surface at all.

The vendor described the mechanism in September 2026, and two parts of it change what a fallback means for a test. The backup is not a fixed alternate per provider. It comes from a platform-managed ordered pool, filtered to models that have not already failed and that the plan allows, and the pool changes over time. So a fallback target cannot be predicted or reproduced, only read after the fact, and a fallback is never a stable second arm in an A/B. More consequential, the selected reasoning effort carries into the fallback attempt only when the backup model supports it, and is otherwise adjusted to a supported value. A bot pinned to a reasoning level by measurement can be served at a different level, and the indicator flags the model swap without mentioning the effort change. Three smaller facts: triggers include a disabled or unavailable model and any retryable error, explicitly including outages, overload, timeouts, and rate limits, so a run that dies at the completion ceiling may have spent an attempt falling back on the way. Billing follows the model that actually served the run, so a credit anomaly is consistent with a fallback rather than ruled out by one. And the indicator names the served model but not the originally selected one, so once a bot's configured model has changed, what an old run fell back from is unrecoverable. Check the toggle before tuning, and when you need a rate rather than a single verdict, ask the vendor for per-agent counters, which carry no user content and work on every privacy tier.

**A bot's `updatedAt` is not evidence its prompt changed.** Nightly platform processes restamp most bots in a workspace within minutes of one another, so a timestamp that lines up suggestively with the date a user started complaining usually means nothing. Reading one as a prompt change has produced a confident, detailed, and entirely wrong account of a regression, caught only by checking version-controlled exports, which are the only reliable record of when content actually moved (source-of-truth reference).

**"Access denied" is three different surfaces.** A guest portal's lockout page uses the literal title "Access denied" with an upgrade or buy-credits message under it, which is the same wording a user reaches for when a file link is broken, and an unauthenticated visit to a deployment URL can render a blank login shell, which is a third surface and says nothing about any file. When a user reports a denied image or download, HEAD the file URL in a fresh browser or with curl first. Image actions return public CDN files (actions reference), so a 200 there means the file is fine and what remains is whether the embed routes the click through an authenticated viewer or an upgrade page.

## What only the UI can test

The completion API cannot attach files. File upload, transcription, and format acceptance can only be tested through the real embed or Studio preview. Keep a tiny known-content test file per format so the check takes seconds.

The embed is more reachable than it looks. A deployment on a public access group serves its form at its embed URL with no sign-in, including on a custom domain, so a browser session carrying no cookies for the host site loads the full form. The real end-user path is drivable in a plain browser, with no admin session, SSO token, or platform login. Several things are reachable only there: file upload fields are invisible to the completions API entirely, form field injection behaves differently from a simulated chat message, and streaming in the embed may outlive the server-side ceiling that kills an API call. Automation that can fill fields and click covers a run without an upload, while a run with an upload needs tooling that can actually attach a file, so check that before planning the test.

Match the transport to the claim being tested, because form testing over the API has three levels, not two. A bare `message` string bypasses the form entirely, and that includes the frame's static instruction prose, not just the field values. On the `message` path the model runs on the Role and Model Reminder alone, which can be a small fraction of the production prompt, and setting the bot's `type` to form-chat does not change that, since it is a property of the transport. An `inputs` object keyed by the frame's `userinput:*` field ids drives the real form path, including what the model does with a full document. But even `inputs` text arrives already extracted, so it proves nothing about whether the platform parses a real user's uploaded file. An API reproduction that passes clean text does not clear the file-handling path, so when a user reports garbled or partial content from an upload, state which layer a passing test actually covered.

Two techniques sharpen transport testing. To prove a field reaches the model in one run, plant a canary phrased so obeying it is consistent with the output contract, such as a substitution rule ("the input word X is a mistranscription, always replace it with Y"), and pair it with the same instruction pasted inline as a positive control. And treat a pasted frame as exploration only. In one measured case an A/B over the pasted-message path showed a candidate prompt destroying pre-existing content in 7 of 8 runs against 0 of 8 for the old prompt, while the same comparison over `inputs`, same size and same input, showed no difference at all. An A/B can be internally consistent and still not generalize off its transport, so explore on the cheap path, conclude on the path real traffic takes, and record in any writeup how the frame was delivered.

The no-fetch limitation doubles as an error-path test. Sending a URL as a bare string does not run the platform's fetch, so the call lands on whatever branch the prompt defines for "no usable content arrived," which makes that branch testable on demand even though the natural failure it stands in for cannot be scheduled. Paste representative content directly into the field to test the happy path the same way. Both halves are prompt-level tests only.

One backend capability is testable without the picker. `document_upload` bypasses the embed's file-type whitelist entirely, and its response carries a `rawStorageUrl` pointing at the plain text the platform extracted, including transcription for audio. Fetch that URL and compare it against known content: if the text comes back right, the backend handles the format and only the client widget blocks it, which is a much smaller fix to request from the vendor. The upload travels base64 in the request body, so use the HTTP transport, and omit the Pickaxe id so the test document lands unattached in the workspace library. A test recording that states its own purpose out loud makes the check unambiguous.

## When the vendor ships a fix you asked for

Two habits, either side of the fix.

Verify the fix rather than trusting the announcement. A support reply saying a behavior is now live is a claim, not a result, and this platform has shipped a fix that passed through unstable intermediate states before settling, so a tool that depends on the fixed behavior can break after the all-clear. Re-run the original reproduction. Read current state before writing anything, because the experiment may already exist: in one case the reproduction needed a configuration different from the value a record was written under, and someone had already changed that configuration for unrelated reasons, so one read replaced a two-write test.

Then find everywhere you wrote the old behavior down. A bug worth reporting is usually a bug worth recording, so by the time it is fixed the old behavior has been promoted into project instructions, per-tool notes, and anything queued for publication, and the most dangerous copies are the most confident, of the form "never trust field X." One fixed read-path bug left three separate instruction-file entries asserting the old behavior, one of them a standing rule, plus two lessons queued for a public repository whose history is permanent. Grep for the bug's keywords across instruction files, notes, and publication queues, and correct each hit. When rewriting, keep the part that outlasted the fix: a bug report usually contains a durable technique next to the perishable defect, and demoting the defect to a dated worked example preserves the technique without asserting something untrue.
