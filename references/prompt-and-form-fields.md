## The three prompt fields

A Pickaxe has three places to put instructions, and they behave differently across a conversation:

- **Role** (`role` in the API). The system prompt. It persists across every turn, so all persona, rules, formatting requirements, and catalog data that must survive follow-up questions belong here. For Form + Chat tools this matters doubly, because the prompt frame fires once and then the conversation continues on the Role alone.
- **Prompt Frame** (`promptframe`). The first user-turn message for form tools. It fires once, injecting form answers via `[bracketed variables]`. Handlebars-style `{{#if}}` conditionals are not supported. Express conditional logic through labeled form options instead ("If the user chose Proposal Comps, then..."). And because there are no conditionals, any frame prose about an optional input runs on every submission, including blank ones. A frame that asserted "the user has also uploaded a full-page screenshot" made the model score visual items from an artifact it never received, on every run where the optional upload was empty. Write frame prose for the empty case and treat the filled case as the branch, and read the frame and the Role together against the same blank-field scenario, because each can look correct alone.
- **Model Reminder** (`responseprefix`). Invisibly prepended to every user message. It is the backstop against instruction drift on long conversations, so reserve it for the few most critical non-negotiable rules rather than duplicating the Role. It is not free and it does not always work, so measure it like any other change rather than adding one whenever a rule is missed. On a single-turn form tool with an empty reminder and a known compliance defect, six rules were written into it, each aimed at a defect already measured on that tool. Across twelve runs against a control, split over two staging bots for a swap, the target metric moved from 71 to 73 percent, which is noise, two other metrics did not move, mean runtime rose 16 percent, and one run came within thirty seconds of the completion ceiling. A reminder helps most where drift is the actual mechanism, meaning long multi-turn conversations, and a single-turn form run gives it much less to do. On a tool already running near the ceiling, a reminder that measures as a null is a loss rather than a neutral.

## The prompt frame is stored twice

`rawpromptframe` is an HTML rendering of `promptframe`, stored independently and not derived from it. Update both consistently or the builder UI and the runtime drift apart. Converting plain to raw: escape `&`, `<`, `>` and turn newlines into `<br>`.

Those rules cover editing prose around an existing field. Adding a field takes more. The plain frame gets the JSON descriptor, and the raw frame needs a matching placeholder element in the same position, keyed by the same id in an id attribute and a duplicate data attribute, marked non-editable, with the descriptor's `example` value as its inner text. A descriptor without its element leaves the runtime and the builder disagreeing about how many fields exist, and a later builder save resolves the disagreement in the builder's favor. One exception: a document upload field's descriptor lives only in the plain frame, and its absence from the raw frame is correct, not corruption.

Two behaviors of the rendered upload field are observable only in a real form. It takes a URL or a dragged file and rejects pasted text (pasting content works only on the completion API's `inputs` path, which is a different pipeline). And submitting before an attachment finishes settling is a silent no-op: the submit control disables, nothing runs, no error appears, and it re-enables minutes later. Wait for the attachment to settle, submit as a separate action, and confirm a new conversation actually started.

## The frame is a sentence, so a field is not the unit the model sees

A prompt frame is usually written as one running sentence with the field descriptors embedded mid-clause, so the frame supplies the punctuation and the connective words and the user's answer supplies only the middle. That has two consequences that no amount of reading the form reveals.

A fixed wrapper reaches only the first sentence of what was pasted. A frame reading `But [field] is in the way.` wraps a one-sentence answer correctly and mangles a paragraph, because the trailing "is in the way" collides with the answer's last clause while "But" still governs its first. Fields sized for a paragraph (a 9,001-character cap is common) invite exactly the input the wrapper cannot absorb.

And the field's label and the frame's wrapper can ask for different things, in which case the wrapper wins, because it is what reaches the model. A field labeled "Who is she and what does she want?" sitting inside a frame that reads `and she wants [field]` renders as "she wants a sheltered young princess who has never been allowed to touch a gun." The label is what the user reads. The frame is what the model reads.

Neither failure is visible from the builder, from the rendered form, or from reading the frame string. Both are obvious the moment the frame is assembled with real answers and the result is read as prose. Six frame-level defects across one family of seven related tools were found that way in a single pass, including a missing space after a period, an orphaned fragment left from an earlier revision with no fields in it, and a label copy-pasted from the field below it. Assemble the frame with realistic answers and read the output before shipping a frame or writing canonical test inputs for one. And when a frame wraps a field in fixed connective words, either write the field's help text to demand the shape the wrapper needs, or reword the frame to absorb ordinary prose, because a user writing naturally will hand the model broken English and the model will work from it without complaint.

## Form field descriptors are embedded JSON

Form fields live as JSON objects embedded inline in the prompt frame string, shaped like `{"id":"userinput:...", "type":"...", "answerlength":..., "example":"..."}`. Preserve them byte for byte when editing the surrounding prose. The safe workflow for programmatic edits:

1. Fetch the live config.
2. Apply exact-match string replacements, asserting each match lands exactly once.
3. Write back, re-fetch, and diff against what you intended to write. Normalize whitespace before declaring a mismatch: the platform rewrites non-breaking spaces (U+00A0) to plain spaces on write, so a byte-exact diff can fail on a perfectly successful write (observed August 2026).

Two behaviors of the descriptors that are not obvious:

- **`example` text is model-visible.** Placeholder examples from the form ("Austin, TX", "Urban Fantasy") can leak into outputs when a user leaves the field blank. Write examples you would not mind seeing in a response, or handle the blank case in the prompt.
- **A field id appearing twice in one frame is corruption.** Guard against it before writing. The converse does not hold across bots: duplicating a Pickaxe keeps the original's `userinput:` UUIDs, so the same field id legitimately appears in tools cloned from one another. Key any cross-tool sweep on the pair (pickaxe, field id), and use the bare id only for corruption checks inside a single frame. A 75-field work list once resolved to 62 distinct ids for exactly this reason, with nothing actually wrong.

## `answerlength` silently truncates input, and truncation fabricates

`answerlength` on a field descriptor is a hard cap on how much of the user's input reaches the model, and the model has no idea text was cut. This produces the classic complaint "the tool only looked at the first part of what I gave it" while every run reports success.

Details that matter:

- On a document upload field, `answerlength` caps the upload **regardless of** the bot's overall `endusertokens` budget. A tool with a million-token budget and a 750-token upload cap reads about one page. Audit for this: in one 88-tool workspace, 47 tools had `answerlength` below `endusertokens`, and a rescan two weeks after the first fixes still found 37 of 53 upload-bearing tools mismatched, because a sweep scoped to a subset silently misses the rest. Check the pair on any upload-bearing tool before trusting a shallow-output complaint.
- The runtime reads only `answerlength` to size a field. But on text fields the builder UI keeps `answerlength` correlated with the declared `type` ("Short Answer" vs "Long Answer"), and it has never been observed pairing "Short Answer" with a large cap. Set both together when raising a text field's cap, or a later save from the builder may clamp the cap back down and silently undo your fix. A document upload field declares its own type and has no short-or-long value to move, so on an upload field raise `answerlength` alone and leave `type` untouched. Ten upload caps raised that way, from 750 and 25,000 up to each bot's `endusertokens`, all read back clean and kept their deployment type. Whether a later builder save clamps an upload cap has not been tested.
- A cheap guard against future silent truncation: have the tool's first output step report the first and last section it received. Truncation then becomes visible to the user instead of masquerading as shallow analysis.

Truncation does not only make output thin. It makes the model invent, because a fragment of a long work leaves gaps that the model fills. An entity-extraction tool whose upload cap admitted roughly the first page of a book-length document produced a full profile for an entity that does not exist in the work, one a character jokes about as if it were real, and misdescribed a genuine entity's attributes and gender. With the cap raised to match the budget, the fabricated entity disappeared from every run and the genuine one was described correctly, including a figure that appears only in the final third. So a complaint that a tool "made something up" on an upload-bearing tool should send you to the field's `answerlength` before you touch the prompt, because a fabrication and a truncation present identically to the user, and fixing the cap can raise accuracy rather than only coverage. Keeping a decoy in the test document, something the text mentions but does not contain, turns this into a fixture (grading reference). Raising a cap also enlarges what the model can leak, so re-measure any content-dependent compliance rule afterward, which the grading reference covers.

## Form to chat conversion, and the chatflag trap

Form + Chat means `type: "form-chat"` plus `enablechatresponses: true`. The `chatflag` field stays false on working form-chat tools, and the reason it must not be flipped is what makes the trap dangerous: the flag is coupled to `type`. Setting it true rewrites `type` from `form-chat` to `chat`, which removes the form entirely and leaves a bare chat box, and setting it false rewrites `type` back. Measured on a live bot in both directions inside one minute, with every other field byte-identical across both writes.

The failure is silent in the worst way, because nothing in the update response or in a read-back of the field you wrote reveals that a second field moved. Two habits follow. Read `type` and `enablechatresponses` before concluding chat is off, since `type: form-chat`, `chatflag: false`, `enablechatresponses: true` means chat is already on and there is nothing to enable. And verify writes against the fields that determine behavior, `type` included, not only against the fields you intended to change, because a diff of your intended fields reports a clean write while the deployment type changes underneath it.

## Sibling tools drift

Pickaxes get built by duplicating an existing one, so a family of related tools usually shares a near-identical system prompt. Those copies then drift, and the drift is invisible from inside any single tool, because each prompt reads as complete and internally consistent on its own. Five sibling tools shared one boilerplate Role. Four carried a one-sentence house style prohibition and the fifth did not, and that fifth tool violated the rule 9 to 15 times per run while the other four produced zero violations across every run of the same test. Nobody had noticed, because nothing in the tool looked wrong. Adding the missing sentence took the next two runs to zero.

When you touch one tool in a family, diff the Roles of the whole family side by side rather than reading the one in front of you. It is cheap over the API, and it finds the rules that were never copied. Run the same check on model, temperature, and reasoning effort, which drift the same way for the same reason.

## Prompt-writing findings that held up

- **Character budgets need word-count proxies.** Most models cannot count characters reliably. When output must fit a hard character limit, set a word cap derived from the domain's real average word length, aim below the limit ("aim for 40 to 48, never exceed 50"), state a floor as well as a ceiling, and include a static good and bad example. Never ask the model to display character counts it cannot compute.
- **Prompt length has a real cost.** Two fixes tested at four runs each reached the same target metric, but the longer one (a full new section vs one sentence appended to an existing rule) degraded two unrelated metrics, apparently by crowding the prompt. Prefer extending an existing rule over adding a section, and always measure the metrics a change was not aimed at.
- **Selection criteria and fidelity rules conflict across fields.** A prompt-frame rule to pick "self-contained" quotes plus a Role rule forbidding edits made the model repair quotes into self-containment, silently rewriting them. When a criterion in one field can be satisfied by violating a rule in another, say explicitly which one governs ("self-contained governs which lines you pick, not whether you may change one").
- **Anti-prompt-leak framing.** Prohibitions on revealing the prompt work better placed at the top of the prompt frame with concrete framing such as "the user will copy your entire response", which makes the leak consequence legible to the model.
- **Exact-reproduction mandates need the word-for-word frame.** Soft mandates ("end the section with this note: ...") get skipped or paraphrased. "Close the section with this exact paragraph, reproduced word for word:" followed by the literal text reproduces reliably. The frame is necessary and not sufficient: the mandate must also name a section the output format actually creates. A correctly framed paragraph anchored to a section the format never defined was skipped in silence, because no moment in composition matched it. Anchor the mandate to a real section name, repeat the requirement inside that section's own format entry, and treat a missing mandated string as a placement bug before treating it as a compliance bug.
- **Image tools must forbid the hyperlink, not only ask for an image.** On an image-action tool the orchestrator can call the action successfully and still hide the result behind a markdown hyperlink (`[Open the finished image](url)`) instead of an inline `![alt](url)`, so users leave the chat to click, which is a different failure from a broken file. A Role that only says "generate and return an image" is not enough: the measured control returned a working public image wrapped in a link. Putting "return `![alt](IMAGE_URL)` on its own line, never a hyperlink" in both the Role and the Model Reminder flipped the next two runs to inline images. Geography and style rules that live only in the Prompt Frame drop on follow-up turns, so the inline-image rule belongs in Role and Reminder if revisions matter.
- **Let the user supply ground-truth numbers.** When a prompt needs an arithmetic fact about a long uploaded document (its total length, a count), the model's own estimate can run materially wrong (an observed 18% undercount on a book-length document) while everything else in the output is accurate, and any math built on the estimate inherits the error invisibly. Add an optional form field for the true number, tell the model to scale its per-section estimates to match it when present, and have it disclose that its total is an estimate when the field is blank. Two qualifiers, measured later. Scaling fixes the total and not the distribution: per-section estimates compress toward the mean, so figures derived from the per-section breakdown stay wrong after scaling, and only figures derived from the total become trustworthy. And the error's magnitude is unpredictable: identical blank-field runs on the same document measured 0.4%, 13.2%, and 20.6% low, so never write a specific magnitude into user-facing copy from one run, and never conclude the estimate is reliable because one run landed close. When a tolerance or threshold claim depends on the number, have the prompt decline to make the claim on the blank branch rather than make it from an estimate.
- **Deliberation can leak into the final answer even with reasoning display off.** On tasks that weigh several options in one completion, the user-facing answer can include scratch-work narration ("this option is worse, let me try another"). This is genuine output text, not the hidden reasoning trace, so no display setting controls it. Instruct the prompt to explore options privately and present only the decided result, quote a real leaked sentence in the rule as an example, and check multi-option outputs for this leak specifically since it hides from a skim for factual correctness. The leak has a second trigger beyond option-weighing: self-censorship. A model wrote a complete list item, judged it inappropriate for the audience partway through, and published the retraction, meaning the abandoned item, a parenthetical questioning it, and the literal words "Replacing this entry:" followed by a substitute. The enumerated count still validated because the model counted the replacement, so a structure check passes while the output is visibly broken. Require every item to be written once in final form with no visible corrections or replaced entries, and screen enumerated output for retraction language.
- **State counts as targets, not quotas.** A hard "produce N items" demand forces padding when honest material runs short, and the padding looks plausible (directory pages formatted as real items, near-duplicates split into separate entries). Frame the count as a target, state outright that a shorter honest list is a successful response, and say where the shortfall should be acknowledged. The boundary condition: this applies where the model retrieves or filters real things, so the honest supply can run out. When the model invents the material (brainstorming from a description), a hard count is safe and worth stating redundantly, in the section headings, the Role, and the reminder together. An enumerated four-sections-of-twelve structure held exactly across six consecutive runs once the count was stated in all three places.
- **Give banned content a legal outlet.** A flat prohibition ("never include expired items") gets violated when the banned material is most of what the model found. Designating a labeled place for it, separate from the main results, ended the violations that the flat ban did not. Prohibition plus outlet beats prohibition alone.
- **A prohibition loses to the instruction that generates the text.** A ban stated in three separate places (a filter step, a section preamble, the Model Reminder) was still violated in 10 of 28 outputs, and the violations clustered in the one slot whose own instruction asked for exactly the concept being banned. Repetition never addressed that, because the generating instruction was doing the work. Move the constraint into the generating instruction itself, at the point where the text is produced, and name a substitution to reach for instead of only a thing to avoid. Measured effect: leakage fell to 2 of 28 and to zero in the worst slot. A constraint enforced far from the text it governs loses to the instruction sitting next to it. The placement fix has a boundary: when the generating instruction asks for a verdict the inputs cannot support, no prohibition on the conclusion holds, because a rule auditing the conclusion against shown arithmetic passes whenever the arithmetic is internally consistent and only the inputs were wrong. Withdraw the request instead. Make the verdict conditional on input quality, ban the adjectives that function as a verdict on the unqualified branch, give that branch a fixed sentence to say, and explain the mechanism so the ban does not read as arbitrary.
- **Rules get satisfied mechanically, so write them against intent.** A rule stated as a category quota ("at least half must be type X") was satisfied with items matching the category while missing the actual audience entirely. Restate such rules in terms of the outcome you mean, include one worked example, and explicitly prefer a shorter list over a technically compliant wrong one.
- **Check that advertised remediation is reachable through the form.** Error and fallback text in a prompt gets drafted against an imagined form, and nothing validates it. One tool's failure message told users to paste page text into a field capped at 100 characters, so the advice had never once been possible, and the corrected message pointed at an upload that the tool's own verification gate would then have rejected. When a prompt tells the user to do something, verify against the live config that the named field can hold the input, and that the rest of the prompt accepts the input once it arrives.
- **Content that arrives unmarked needs a marking rule, not a preservation rule.** A cleanup tool preserved bracketed author notes perfectly and still failed users who dictate, because spoken notes arrive with no brackets to preserve. The output kept every word and dropped the meaning, turning a private note into narrative prose, which is worse than deletion because nothing looks missing. When meaning-bearing markup can be absent from the input, instruct the model to recognize the content and add the markup, and place that rule above any remove-filler rule so the content cannot be classed as filler first.
